# VolvoxAI runtime (`libvolvoxai`)

**One shared library.** This Rust crate builds a single cdylib
(`libvolvoxai.so` on Linux, `libvolvoxai.dylib` on macOS) that exposes the C
inference engine (`../native`) as a
[Synurang](https://github.com/ivere27/synurang) service defined in
[`../proto/volvoxai.proto`](../proto/volvoxai.proto). Rust remains thin FFI
glue over the C engine:

- `src/gen/volvoxai_ffi_plugin.rs` — generated by the Synurang **Rust** generator
  (`lang=rust,mode=plugin_server`): the `VolvoxAiServicePlugin` trait, the FFI
  dispatcher, and the `#[no_mangle] Synurang_*` entry points (unary + streaming).
- `src/lib.rs` — implements that trait by calling the engine over `extern "C"`;
  registers the plugin on load via `ctor`. No inference logic lives here.
- `build.rs` — `prost_build` compiles the proto into message types, and `cc`
  compiles the native C engine (minus `native/cli/main.c`) straight into this
  cdylib. On macOS it also compiles `native/src/backends/metal_engine.m` and
  links Foundation and Metal.

The result is one shared library that serves **FFI** (loaded in-process) and
**TCP** with the same code — the transport is chosen by the caller. Streaming
`Generate` works (the Rust generator emits a real `PluginStreamSender`).

A complete C++ receipt-training client is available in
[`../examples/tiny_receipt_vqa/tiny_receipt_vqa_train.cc`](../examples/tiny_receipt_vqa/tiny_receipt_vqa_train.cc),
with build, dataset, artifact, and resume instructions in
[`../examples/tiny_receipt_vqa/README.md`](../examples/tiny_receipt_vqa/README.md).

## Build

```bash
make build_codegen_tool     # Linux: fetch + verify pinned Synurang v0.7.2 under build/cache/
make build_server           # compile shaders, regenerate Rust RPC glue, build the library
# -> runtime/target/release/libvolvoxai.so (Linux)
```

The verified generator auto-download currently supports Linux x86-64 and
AArch64. A macOS build must provide a compatible generator explicitly with
`PROTOC_GEN_SYNURANG_FFI=/path/to/protoc-gen-synurang-ffi`; without that
override, `make build_server` intentionally stops before Cargo. Once supplied,
the build emits `runtime/target/release/libvolvoxai.dylib`.

`make proto_codegen` generates all bindings from `../proto/volvoxai.proto`:
dependency-free C lite messages and the C native header under `generated/c/`,
the TypeScript client/lite pair under `generated/typescript/`, and Rust plugin
glue under `src/gen/`. `make proto_codegen_check` regenerates into a temporary
directory and fails if checked-in output is stale or contains an obsolete
Synurang-generated file. Per-mode manifests let subset targets such as
`proto_c_lite` replace only their own outputs without deleting another mode's
files. The C artifacts belong only to this optional service runtime and are not
composed into either fixed native profile. Set
`PROTOC_GEN_SYNURANG_FFI=/path/to/protoc-gen-synurang-ffi` to use an explicit
compatible generator.

Synurang v0.7.2's self-contained C-lite and TypeScript targets are generated
from a local `volvoxai.v1.Empty` and explicit repeated `StringEntry` /
`TensorShapeEntry` messages. Their protobuf wire encoding is identical to the
previous `google.protobuf.Empty` and `map` fields, but their generated source
APIs are different: regenerate downstream clients and treat those fields as
entry arrays. When duplicate keys arrive, the runtime preserves protobuf map
semantics by using the last value.

Needs Docker for the reproducible shader compiler, plus a Rust toolchain and
`protoc`. A direct `cargo build` requires `make compile_shaders` once first.
Linux builds also need `libvulkan-dev` (for
`native/src/backends/vulkan_engine.c`, same as the Docker image). macOS Metal builds need
Xcode Command Line Tools plus Vulkan headers through `VULKAN_SDK`, because the
runtime still compiles its runtime-loaded Vulkan backend. Clients generate their
own bindings from the same proto in their language (`lang=dart`, `lang=go`, …)
and load the platform library or dial it over TCP.

## Reality check

The engine is a **global singleton** (`native/src/runtime/engine.c`), so the runtime
serializes every call behind one mutex and keeps **one model loaded at a time**;
`model_id` is a validation token over that single context. True multi-model /
concurrent inference needs per-context state in the engine.

`PatchGraph` targets the current numeric node index. Its batch is transactional,
structural edits force a rebuilt plan, and `reoptimize=true` reruns graph fusion.
`declared_outputs` is presence-sensitive: omit to preserve default `Run` outputs,
send an empty list to clear them, or provide graph-produced tensor names to
replace them. `TrainStep` rejects duplicate/non-F32 trainables and pins the
native base route, so an active staged adapter remains active and unchanged;
explicit LoRA branches in the graph remain trainable.
The native training update and optimizer step commit before an optional
safetensors flush; a file-save error does not roll back that live update.

Vulkan, OpenGL, and (in a macOS build) Metal are initialized when explicitly
selected in `ExecOptions` on model creation/loading. An unavailable requested
backend returns an error; it does not silently fall back to CPU. Backend
selection is model-scoped, and training inherits that backend. A GPU `TrainStep`
also fails if its complete backward plan is unsupported instead of silently
executing the backward pass on CPU. OpenGL contexts are rebound to each
serialized service worker call because TCP/streaming calls are not thread-affine.

The library embeds the full compressed shader pack, so deployment does not need
a shader directory. For development, set `VOLVOXAI_SHADER_DIR` to a generated
`native/shaders` tree; the runtime logs once when those external files are used
and falls back to the embedded copy when an override is unavailable.
