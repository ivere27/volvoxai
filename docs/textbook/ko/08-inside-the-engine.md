## 8.1 하나의 그래프, 세 프로바이더 (계층)

> 🌱 **아이디어.** 같은 모델을 브라우저에서 "가장 화려한 하드웨어" 부터 "언제나 어디서나 동작" 까지 세
> 가지로 돌릴 수 있고, VolvoxAI가 기기가 주는 가장 좋은 것을 고릅니다. 모두 *같은* 답을 계산합니다 —
> 누가 산술을 하느냐(GPU 또는 CPU)와 숫자가 어디 사느냐만 다릅니다.

🔧 1장 상기: VolvoxAI는 브라우저에서 같은 그래프를 세 가지로(플러스 네이티브 바이너리) 돌릴 수
있습니다. **누가 산술을 하는지** 와 **텐서가 어디 사는지** 만 다릅니다.

```mermaid
flowchart TD
    G["graph.json + safetensors"] --> L["ModelLoader.load()"]
    L --> S["Model.capture()"]
    R["VolvoxAI.createRuntime()"] --> C["Runtime.compile(snapshot, { backend: policy })"]
    S --> C
    C --> T1["WebGPU 프로바이더<br/>컴파일된 GPU 경로"]
    C --> T2["WASM 프로바이더<br/>선형 메모리 위 컴파일된 C 커널"]
    C --> T3["CPU 프로바이더<br/>참조 커널"]
```

- **Tier 3 — 순수 JS** (`ts/ops/*.ts`): 책 내내 읽은 소박한 커널. 느리지만 단순하고 의존성 없음.
  **기준(ground truth)** 입니다: 모든 빠른 계층이 이것과 대조됩니다.
- **Tier 2 — WASM**: 같은 연산을 SIMD로 WebAssembly에 컴파일합니다. 범프 할당기가 모든 텐서를 하나의
  평평한 선형 메모리 블록에 넣고, 컨텍스트 실행이 컴파일된 C 커널을 호출합니다. 순수 JS보다 종종
  5–50배 빠릅니다.
- **Tier 1 — WebGPU**: 지원되는 연산은 GPU **컴퓨트 셰이더** 가 됩니다. 컴파일이 가중치를 VRAM에
  올리고 선택한 경로를 만들며, 실행은 인접 GPU 노드 사이 호스트 읽기 없이 이를 재생합니다. 필수 경로가
  지원되지 않으면, 호출자의 컴파일 정책이 연산 폴백을 명시적으로 허용한 경우가 아닌 한 컴파일이
  실패합니다. 실행은 노드를 조용히 건너뛰지 않습니다.

🔬 설계 원칙: **컴파일 시점에 유효한 경로를 고르고 증명합니다.** 컴파일 보고서는 선택한 프로바이더,
경로 증거, 그리고 프로바이더가 제공할 수 있을 때 디바이스 식별자를 기록합니다. 그 경로는 컴파일된
모델에서 고정되며, 실행 오류가 생기면 다른 백엔드를 조용히 시도하지 않고 오류를 보고합니다.

### 🔬 컴파일러가 shape에 대해 가정해도 되는 것

이 원칙은 컴파일러가 **그 모델이 앞으로 실행하게 될 shape 전체**를 볼 수 있을 때만 성립합니다. 샘플
shape 하나에 대해 경로를 증명해봐야 다음 요청에 대해서는 아무것도 증명하지 못합니다. 그래서 그래프는
자신의 shape 도메인을 미리 선언해야 하고, 그 선언은 **반드시 함께 와야 하는 두 가지 성질**로 이뤄집니다.

차원 심볼에는 **이름이 있습니다.** 그래프가 토큰 id를 `["B", "S"]`로, 임베딩을 `["B", "S", 768]`로
적으면 두 곳의 `S`는 *하나의* 크기입니다. 시험한 날 우연히 값이 같았던 두 숫자가 아닙니다. 컴파일러는
이 등식을 사실로 사용할 수 있습니다.

차원 심볼에는 **경계도 있습니다**: `{ "S": { "min": 1, "max": 2048 } }`. 도메인이 유한하므로 "이
그래프가 최대로 필요로 할 활성값 크기"가 컴파일러가 실제로 계산할 수 있는 숫자가 되고, 백엔드는 그
숫자를 자신의 실제 버퍼·바인딩·디스패치 한계와 대조할 수 있습니다.

재미있는 부분은 **어느 한쪽만으로는 안 된다**는 점입니다:

- **이름 없이 경계만.** 모든 축이 2048 미만인 건 알지만, id의 시퀀스 축과 임베딩의 시퀀스 축이 같은
  2048이라는 보장은 없습니다. 둘을 곱해 합치는 attention 연산이 불일치를 발견하게 되는데, 그 시점은
  실행 중이고 장소는 커널 안입니다. 문제를 발견하고 싶지 않은 바로 그 자리죠.
- **경계 없이 이름만.** 두 축이 같은 `S`라는 건 알지만 `S`에 최댓값이 없으니 최악의 텐서 크기는
  무한입니다. 증명할 숫자 자체가 없으므로, 남는 정직한 선택지는 실제 요청이 올 때까지 기다렸다가 그때
  특수화하는 것뿐입니다. 이 설계가 없애려는 바로 그 "조용한 폴백"입니다.

둘이 함께 있어야 질문이 결정 가능해지고, 그것이 위 문단의 보장을 사는 값입니다. 컴파일이 성공한
순간부터 선언된 도메인 안의 모든 shape는 증명된 경로를 갖고, 실행은 두 번째 경로를 찾아 나설 일이
없습니다.

대신 치르는 값은 분명하고 의도된 것입니다 — 이제 경계를 **직접 선언해야** 하고, 경계를 잘못 적은
그래프는 절뚝거리며 도는 대신 컴파일 시점에 거절됩니다. 브라우저 탭이나 로봇으로 나가는 모델이라면,
빌드 시점에 "안 된다"는 답을 듣는 쪽이 훨씬 싼 결말입니다.

## 8.2 소박한 커널이 느린 이유

> 🌱 **아이디어.** 우리가 읽던 단순 루프는 한 번에 곱셈 하나를 하고, 숫자를 찾아 메모리 곳곳을
> 뜁니다. 여덟 손을 가진 계산원이 하나만 쓰고, 물건마다 가게 뒤편으로 걸어가는 것과 같습니다. 칩은
> 대부분 계산이 아니라 *기다리고* 있고 — 할 수 있는 것의 몇 퍼센트만 씁니다.

🔧 3장의 소박한 `Conv2D` 를 다시 보세요: 일곱 중첩 루프, 한 번에 곱셈 하나. *올바르지만*, 현대 CPU는
두 이유로 싫어합니다:

1. **SIMD 유닛을 낭비합니다.** CPU 코어는 *한* 명령으로 8개(AVX2) 이상의 실수를 곱할 수 있습니다.
   소박한 루프는 하나… 씩… 해서, 실리콘의 일부만 씁니다.
2. **캐시를 뒤흔듭니다.** RAM은 CPU보다 ~100배 느립니다. 코어는 최근 쓴 데이터를 작고 빠른 **캐시** 에
   둡니다. 소박한 conv는 메모리 곳곳을 뛰어(스트라이드 이미지 읽기), 계산 대신 RAM을 계속 기다립니다.

결과: 소박한 커널은 칩 실제 처리량의 **2–5%** 만 쓸 수 있습니다. 최적화는 SIMD 유닛을 먹이고 캐시를
존중하는 것입니다.

> 🔬 **뜯어보기: 계산 병목 대 메모리 병목(루프라인).** 모든 커널은 두 천장 중 하나에 막힙니다 — 칩이
> 초당 할 수 있는 곱셈-덧셈 수, 아니면 RAM에서 바이트를 옮기는 속도. 어느 쪽이 무느냐는 **산술
> 강도(arithmetic intensity)** — 로드한 바이트당 FLOP — 가 정합니다. 1×1 conv는 로드한 가중치를 여러
> 픽셀에 재사용해(강도 높음 → 계산 병목, SIMD가 도움) 반면 원소별 `Add` 는 바이트를 한 번만
> 만집니다(강도 낮음 → 메모리 병목, SIMD를 더 써도 *소용없음*). 그래서 융합(§8.4)과 버퍼
> 재사용(§8.5)이 빠른 matmul만큼 중요합니다: 계산 천장이 아니라 메모리 천장을 공략하니까요. 캐시 계층도
> 축소판 같은 이야기입니다 — L1 히트는 몇 사이클, RAM 왕복은 수백.

## 8.3 소박함에서 빠름으로: 같은 수학, 재배열

> 🌱 **아이디어.** 빠른 버전은 *정확히* 같은 것을 계산합니다 — 칩의 여러 손이 바쁘게, 필요한 숫자가
> 이미 가까이 있도록 일을 재조직할 뿐입니다. 데이터를 깔끔히 줄 세우고, 칩이 아주 잘하는 행렬 곱에
> 건네고, 명령당 곱셈을 여럿 하고, 코어에 나눕니다. 올바름은 단순 버전에 살고, *속도는 배치에
> 삽니다.*
>
> *같은 합, 빠른 경로:* 숫자 한 열을 더하면 위에서 아래로 가든 짝지어 묶든 합은 같습니다 — 다만 한
> 순서는 두 손을 동시에 쓰게 할 수 있지요. 빠른 커널은 덧셈의 *순서와 묶음* 만 바꾸지, 합은 결코
> 바꾸지 않습니다.

🔧 최적화된 커널은 *무엇을* 계산하는지(출력은 Tier 3과 동일)는 절대 바꾸지 않습니다 — 일의 *순서와
배치* 를 바꿉니다. VolvoxAI의 핫 경로는 밀집 층의 `native/src/kernels/gemm_f32.c` 와
`packed_quant_gemm.c`, `conv_f32_isa.c`(fp32 합성곱), `quant_cpu_isa.c`(int8 합성곱)를 포함합니다.
주요 기법:

| 기법 | 아이디어 | 성과 |
|---|---|---|
| **im2col + GEMM** | conv 패치를 큰 행렬로 펴고, 빠른 행렬 곱 호출 | 수십 년의 튜닝된 matmul 재사용; SIMD 먹임 |
| **포인트와이즈 GEMM** | 1×1 conv는 *곧* 행렬 곱 — 직접 그렇게 취급 | 단일 최대 이득(대부분 conv가 1×1) |
| **가중치 프리패킹** | 내부 루프가 읽는 정확한 순서로 로드 시 한 번 재배치 | 캐시 미스 읽기를 순차 읽기로 |
| **블로킹/타일링** | 캐시에 맞는 작은 타일을 처리한 뒤 이동 | 데이터가 뜨거운 동안 재사용 |
| **SIMD (AVX2/NEON)** | 명령당 8–32 곱셈-덧셈 | 사이클당 산술 ~8–32배 |
| **멀티스레딩** | 출력 행을 CPU 코어에 분배 | 그 위에 ~코어수배 |

```
소박한 conv                     최적화된 conv (im2col + GEMM)
 각 출력 픽셀마다:               [1] 입력 패치를 펴 큰 행렬로  (한 번)
   각 필터 탭마다:               [2] 하나의 크고, 캐시 친화적, SIMD, 스레드된
     스칼라 곱 하나                  프리팩된 가중치와의 행렬 곱
 (흩어진 메모리, 1레인)          (순차 메모리, 여러 레인, 여러 코어)
```

> **이 저장소의 실제 결과.** 🌱 한 메모리 절약 변경으로 탐지기가 RAM을 **~5배 적게** 쓰고 눈에 띄게
> 빨라졌습니다 — 같은 답, 훨씬 가벼움. 🔬 *아레나 버퍼 재사용 계획기*(노드마다 새로 할당하지 않고
> 스크래치 메모리 재사용)를 더해 피크 메모리를 **88.8 MB → 18.8 MB** 로 줄였고, 포인트와이즈-GEMM
> 경로와 합쳐 EfficientDet 순전파를 의미 있게 빠르게 해 — 구글 TFLite/XNNPACK과의 격차를 ~1.16배(웜)로
> 좁혔습니다. *그것이* 커널 엔지니어링입니다.

교훈: **올바름은 소박한 커널에 살고, 성능은 메모리 배치에 삽니다.** `ts/ops/conv2D.ts` 를 읽은 뒤
`native/src/kernels/conv_f32_isa.c` 와 diff해, 그 기예의 두 반쪽을 보세요.

> 🔬 **뜯어보기: im2col은 공짜가 아니라 — 그래서 빠른 경로는 종종 건너뛴다.** 펼친 패치 행렬을
> 실체화하면 입력이 대략 `k_h · k_w ×`(3×3 conv → 잠깐 ~9배 메모리) 부풀어 오릅니다. 큰 conv 하나엔
> 괜찮지만, 여기의 *많은* 1×1 conv엔 펼칠 게 없습니다 — 1×1 conv는 이미 행렬 곱이니까요 — 그래서
> "포인트와이즈 GEMM" 이 단일 최대 이득입니다. 프로덕션 커널은 **암시적 im2col** 도 씁니다: GEMM 루프
> 안에서 원본 텐서로 바로 인덱싱해, 큰 행렬을 만들지 않고 matmul의 속도를 얻습니다.

### 🔬 밀집 행렬 곱의 해부

같은 패턴이 이제 `MatMul`/`Linear`/`Gemm` 에 직접 나타납니다. 네이티브 CPU와 WASM은 불변 가중치를
여덟-출력 패널로 한 번 패킹하고, 레지스터에서 4행×8열을 계산하며, 보수적 32 KiB L1D의 75% 아래로
유지되도록 K를 청크로 걷습니다. 그 폴백 캐시에서 F32 커널은 `KC=496` 을 골라 24,576바이트 예산 중
23,936을 씁니다. 네이티브는 호스트 L1D 정책을 자동 감지·캐시하고, WASM은 브라우저가 캐시 토폴로지를
노출하지 않아 이식 가능한 32 KiB 가정을 유지합니다.

GPU는 같은 재사용 문제를 다르게 풉니다. 8x8 워크그룹이 협력해 16x16 A/B 타일을 워크그룹 메모리에
로드해 16x16 출력 타일을 만듭니다. 그것은 CPU식 지속 가중치 패킹이 아니라 **타일링** 입니다. 단일
토큰 디코드(`M=1`)와 작은 행렬은 공유 타일 채우기가 이득보다 비쌀 수 있어, 더 단순한 스칼라 셰이더나
전용 CPU 마이크로커널을 유지합니다. 순수 JS 커널은 공부하기 쉬운 참조로 남습니다.

그 마지막 선택이 중요합니다: "최적화된 MatMul" 은 하나의 영리한 루프가 아닙니다. 자료형·형태·기기가
고른, 패킹·캐시 블로킹·레지스터 타일링·워크그룹 타일링·저오버헤드 디코드 경로 사이의 디스패처입니다.

## 8.4 연산 융합: 메모리를 그만 만지기

> 🌱 **아이디어.** 단계 사이에서 기계는 보통 결과를 적어 두고 다음 단계가 다시 읽습니다 — 큰 데이터엔
> 낭비되는 왕복이 많습니다. **융합** 은 이웃 단계를 붙여 데이터를 한 번만 만지게 합니다: "곱하고 *동시에*
> 클램프" 를 한 번에, 둘 대신. 수백 단계에 걸쳐 그 모든 적고-다시-읽는 왕복을 건너뛰면 실제 속도가
> 됩니다.

🔧 연산 사이에서 결과는 메모리에 쓰이고 다음 연산이 다시 읽습니다. 큰 특징 맵에선 데이터를 *옮기는*
것이 수학보다 비쌀 수 있습니다. **연산 융합** 은 인접 연산을 병합해 데이터를 한 번만 만지게 합니다.
VolvoxAI는 컴파일 시점 융합 패스를 돌립니다(`native/src/runtime/graph_opt_fusion.inc`):

```
융합 전:  Conv2D ─▶ [특징 맵 쓰기] ─▶ ReLU6 ─▶ [다시 쓰기]
융합 후:  Conv2D+ReLU6 ─▶ [한 번 쓰기, 이미 활성화됨]
```

🔬 적용하는 융합 패턴(`docs/operator_fusion_patterns.md` 참고):

- **Conv + ReLU6** → conv의 재양자화 단계 안에서 바로 클램프(3–4장에서 `relu` 가 커널에 접힌 것을
  봤지요).
- **연쇄 `Add`** → 여러 잔차를 한 패스로 합산.
- **뎁스와이즈 → 포인트와이즈** → 중간을 흘리지 않고 MBConv 쌍을 연달아 실행.
- **Concat + Sigmoid**, **별칭 제거**(일부 `Reshape` 같은 no-op 복사 제거).

각 융합 쌍은 큰 텐서의 전체 읽기+쓰기 한 번이 줄어듭니다. 262개 노드에 걸쳐 쌓이지요.

## 8.5 메모리: 텐서는 일시적이다

> 🌱 **아이디어.** 모델이 만드는 숫자 대부분은 스크래치 작업입니다 — 잠시 필요하고 다시는 안 씁니다.
> 단계마다 새 종이를 꺼내는(그리고 거대한 뭉치가 필요한) 대신, 엔진은 옛 스크래치가 끝났음을 알아채고
> **같은 종이를 재사용** 합니다. 그래서 숫자가 수백 메가바이트에 이르는 모델도 그 일부의 메모리로 돌
> 수 있습니다.

🔧 미묘하지만 중요한 점: 순전파의 텐서 대부분은 **스크래치** 입니다 — 잠깐 필요하고 다시 없음(예:
어텐션 MatMul이 소비하면 `ln1_0` 은 죽음). 소박한 엔진은 노드마다 새 버퍼를 할당(단순하나 낭비).
똑똑한 엔진은 수명이 겹치지 않아 메모리를 공유할 수 있는 버퍼를 **계획** 합니다 — 위에서 말한 **아레나
버퍼 재사용 계획기**. 그래서 VolvoxAI는 텐서 *합* 이 수백 MB인 모델을 그 일부의 피크 RAM으로 돌 수
있습니다: 같은 물리 바이트를 노드마다 재활용.

> 🔬 **뜯어보기: 버퍼 재사용은 그래프 색칠이다.** 계획기는 각 텐서의 **생존 구간(live interval)** —
> 그것을 쓰는 노드부터 마지막으로 읽는 노드까지 — 을 계산한 뒤, 두 텐서의 구간이 겹치지 않을 때만 같은
> 버퍼를 줍니다. 컴파일러가 많은 변수를 적은 CPU 레지스터에 담을 때 푸는 바로 그 문제입니다(레지스터
> 할당 / 구간 색칠). 그래서 탐지기 피크 메모리가 **88.8 MB → 18.8 MB** 로 떨어졌습니다: 텐서가 줄어서가
> 아니라, *동시에 살아있는* 텐서가 줄어 같은 물리 바이트를 공유해서입니다.

```
노드 수명 (─ = 살아 있음):     버퍼 재사용:
  A: ───                          A와 C는 안 겹침 → 같은 버퍼를 줌
  B:   ─────                      B와 D는 안 겹침 → 버퍼 공유
  C:      ────
  D:          ───                 텐서 4개, 물리 버퍼 2개
```

🔧 이 그림이 조용히 전제하는 게 하나 있습니다: A, B, C, D가 각각 얼마나 *큰지* 안다는 것. 그래프에
심볼 `S` 가 있으면 모릅니다 — 요청이 알려주기 전까지는요. 어느 수명이 어느 것과 겹치는지는 토폴로지가
정하고 컴파일 시점에 결정됩니다. 각 칸이 몇 바이트 필요한지는 그렇지 않습니다. 이 두 질문을 갈라놓는
것이 다음 절의 주제입니다.

## 8.6 요청마다: shape 하나를 바인딩하기

> 🌱 **아이디어.** §8.1이 공장 검수였다면 — 기계를 내보내기 전에 앞으로 받을 모든 주문을 처리할 수
> 있음을 증명하는 것 — 이 절은 주문 하나가 실제로 들어오는 장면입니다. 기계는 이 일을 할 수 *있다* 는
> 걸 이미 아니까 새로 알아낼 게 없습니다. 작업 공간을 알맞게 재어 두고 돌리면 끝이지요. 그리고 대부분의
> 주문이 직전 주문과 비슷하니, 최근 작업의 치수를 매번 다시 재지 않고 작은 선반에 얹어 둡니다.

🔧 구체적인 입력과 함께 요청이 도착합니다. 백엔드 상태에 단 1바이트를 쓰기 전에, 컨텍스트는 다음을
순서대로 합니다:

1. 선언된 모든 공개 입력을 **검증** — 이름, dtype, 랭크, 각 차원의 경계와 `multiple_of`, 정확한
   바이트 수. 입력이 빠지면 오류이며, 버퍼 길이로 형태를 추론하는 일은 없습니다.
2. 심볼을 **바인딩**. `tokens` 가 `[1, 6]` 으로 오면 `S = 6` 이 바인딩됩니다. 두 번째 입력이
   `S = 5` 를 주장하면 충돌이고, 어텐션 커널 안이 아니라 여기서 거절됩니다.
3. 그 바인딩으로부터 모든 중간·출력 형태를 **해석** 하며, 각 노드의 출력 단언을 함께 확인합니다.
4. 이 구체 크기에 대해 연산·양자화·산술·메모리 한계를 **예비 점검(preflight)**.
5. 바인딩과 용량 증가를 원자적으로 **커밋**.
6. *그제서야* 입력을 복사하고, 커널을 디스패치하고, 출력을 스냅숏합니다.

이 순서가 핵심입니다. 1–4 어디서 실패하든 직전의 성공한 바인딩·용량·디코드 상태가 그대로 쓸 수 있게
남습니다 — 절반만 변형된 컨텍스트가 아니라 오류를 받습니다.

### 🔧 plan 캐시: 방금 구한 걸 또 구하지 않기

2–4단계는 순수 메타데이터 작업이지만 공짜가 아니고, 비슷한 요청을 받는 서버라면 이걸 끝없이 반복하게
됩니다. 그래서 각 컨텍스트는 정확한 **shape 서명(shape signature)** 을 키로 하는 작은 **plan 캐시** 를
둡니다. 서명은 모든 공개 입력의 이름·랭크·축으로 만든 정규 문자열입니다. `S = 6` 인 TinyStories라면
(입력은 정규 바이트 순서, 각 필드 앞에 길이가 붙습니다):

```text
v1|9:positions|2:1,6|6:tokens|2:1,6
```

서명이 같으면 해석된 plan을 재사용합니다. 캐시는 컨텍스트마다 하나이고(두 컨텍스트가 공유하지 않음),
LRU이며, 항목 수 **와** 메타데이터 바이트 **둘 다** 로 제한됩니다 — 기본값은 8개와 16 MiB
(`ts/core/CPUShapeExecutionContext.ts` 의 `CPUShapeExecutionContextOptions`). 바이트 예산보다 큰 plan은
다른 걸 다 몰아내는 대신 그냥 캐시하지 않습니다.

> 🔬 **왜 해시가 아니라 문자열인가.** 서명 자체가 정확성의 키입니다. 조회를 위해 해시할 수는 있지만,
> 해시 충돌이 형태 동일성을 성립시키게 두어서는 안 됩니다. 여기 서로 다른 세 가지 정체성이 있다는 점도
> 보세요: 정확한 `ShapeSignature` 는 *정확성* 을 결정하고, 더 좁은 tactic 서명은 *어느 커널 변형* 인지를,
> 더 성긴 capacity class는 *어느 할당을 재사용* 할지를 결정합니다. 이것들을 한 키로 뭉치면 과도하게
> 특수화하거나, 조용히 잘못된 plan을 재사용하게 됩니다.

### 🔧 capacity 풀: 최댓값이 아니라 최고 수위에 맞춰 할당하기

이제 §8.5가 남긴 질문으로 돌아갑니다. `S = 6` 만 보내고 있는데 엔진이 `S = 256` 을 위해 할당하지는
않습니다 — 그건 패딩의 메모리 비용을 뒷문으로 다시 들이는 셈이니까요. 대신 각 컨텍스트가 **capacity
풀** 하나를 소유합니다:

- 텐서 칸의 용량은 바인딩이 현재 가진 것보다 더 필요할 때만 자랍니다.
- 성장은 **기하급수적**(기본 ×2)이라, 위로 표류하는 워크로드도 요청마다가 아니라 몇 번만 재할당합니다.
- 용량은 컨텍스트가 사는 동안 줄지 않으므로, 안정적인 워크로드는 처음 몇 번 이후 할당을 아예 멈춥니다.
- 성장은 트랜잭션이고 상한이 있습니다(기본 512 MiB): 합법적인 형태가 예산에 못 들어가면 절반만 자란
  컨텍스트가 아니라, 후보 상태를 되돌린 `OUT_OF_MEMORY` 를 받습니다.
- 결과는 정확한 논리 저장소로 복사되어 나가므로, 호출자가 용량 버퍼의 쓰지 않는 꼬리를 보는 일은
  없습니다.

```text
요청 1: S=6    용량  6행   성장 (첫 접촉)
요청 2: S=5    용량  6행   재사용 — 할당 없음
요청 3: S=7    용량 12행   ×2 성장 (7 필요, 12 확보)
요청 4: S=11   용량 12행   재사용 — 할당 없음
요청 5: S=64   용량 96행   12에서 64가 들어갈 때까지 두 배씩 (24, 48, 96)
요청 6: S=11   용량 96행   재사용 — plan 캐시 적중, 할당 없음
```

이건 예시가 아니라 실제 추적입니다: TinyStories에서 저 여섯 요청은 활성값 용량을
1,221,576 → 1,221,576 → 2,443,152 → 2,443,152 → 19,545,216 바이트로 옮기며 성장 이벤트는 세 번이고,
마지막 요청은 할당 없는 plan 캐시 적중입니다.

🔬 이 수치들은 구전이 아니라 들여다볼 수 있는 카운터입니다: `planCacheHits` / `misses` / `evictions` /
`oversizeSkips`, 그리고 `activationCapacityBytes`, `activationCapacityHighWaterBytes`,
`activationGrowCount`, `grownTensorCount`. 네이티브 엔진도 같은 개념을
`dynamic_arena_capacity_bytes` / `_high_water_bytes` / `_grow_count`
(`native/src/runtime/runtime_state.h`)로 추적합니다. 워크로드가 캐시를 들쑤시고 있는지 안정됐는지
알고 싶으면 이걸 읽으세요 — 벽시계 시간으로 짐작하지 마시고요.

> 🔬 **이 과정을 대부분 건너뛰는 두 경우.** **상수 전용(constant-only)** 그래프 — 3장의 EfficientDet
> 패키지처럼 심볼이 아예 없는 것 — 은 합법적인 바인딩이 정확히 하나라, 컴파일이 한 번 해석해 두고
> 실행은 입력 뷰만 검증한 뒤 심볼 바인딩·그래프 전역 추론·캐시 조회를 통째로 건너뛰는 정적 빠른 경로를
> 유지합니다. **디코드** 가 다른 하나입니다: 시퀀스가 토큰마다 하나씩 자라니 토큰마다 재바인딩하면
> 토큰마다 재특수화하는 셈이 됩니다. 대신 디코드는 KV를 경계가 있는 용량까지 확보하고 그 안에서 활성
> 길이를 추적합니다(2장 §2.8). 둘 다 계약을 우회하는 편법이 아니라 계약의 귀결입니다.

🌱 **거래를 있는 그대로.** 동적 shape는 일을 매 요청에서 빌드 시점으로 옮기고, 보내지도 않은 토큰 값을
치르지 않게 해 줍니다. 대신 치르는 것은, 새로운 크기의 *첫* 요청이 실제 작업을 한다는 점입니다 — plan을
해석하고, 어쩌면 버퍼를 키우고요. 정직한 벤치마크라면 어디서든 보이는 cold/warm 격차가 이것이고,
`docs/dynamic-shape-baseline.md` 의 보고서가 하나의 숫자를 내세우는 대신 cold와 warm을 따로 기록하는
이유입니다.

## 8.7 엔진 전체, 한 문장으로

> 🌱 **아이디어 정리.** 같은 답을, 빠르게: 칩의 모든 손 쓰기(한 번에 곱셈 여럿, 여러 코어, GPU),
> 이웃 단계 붙이기, 스크래치 메모리 재사용, 그리고 실제로 받은 요청 크기에 일을 맞추기. 모델이
> *무엇을* 계산하는지는 아무것도 안 바뀌었고 — 칩이 *얼마나 효율적으로* 하는지만 바뀌었습니다.

🔧

> **VolvoxAI는 그래프가 선언한 shape 도메인 전체에 대해 컴파일된 경로 하나를 증명한 뒤, 요청마다 노드
> 목록을 걷습니다 — 구체 shape 하나를 바인딩하고, 각 노드를 사용 가능한 가장 빠른 백엔드의 커널에
> 디스패치하고, 메모리 버퍼를 재사용하고 인접 연산을 융합하면서요 — 소박한 참조와 정확히 같은 숫자를,
> 훨씬 빠르고 작게 냅니다.**

그것이 시스템 전체입니다. 나머지는 연산 하나, 백엔드 하나, 또는 이 골격 위 최적화 하나가 더 있는
것입니다.
